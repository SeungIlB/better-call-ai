# 부족 기능 보완 기록

문서와 현재 구현을 대조해 확인한 미완료 항목을 우선순위대로 하나씩 보완한다. 각 단계는 코드·검증·문서 기록과 로컬 커밋까지 완료한 뒤 다음 단계로 넘어간다. 원격 push는 하지 않는다.

## 전체 계획

1. 다중 자료의 날짜·금액·핵심 사실 차이를 사용자 검토 항목으로 표시한다.
2. 주택 임대차 전용 검색·프롬프트를 사건 도메인 설정으로 분리한다.
3. 차량 사고 도메인 법령·판례·검색·평가를 추가한다.
4. 실제 문서 평가와 법률 전문가 검토를 확장한다.
5. 보존기간 purge, 작업 복구, 요청 제한 등 운영 보완을 진행한다.

## 1. 다중 자료 충돌 표시 — 완료

범위: 날짜와 금액처럼 정규식으로 안전하게 추출할 수 있는 값만 자료별로 비교한다. 값이 다르면 “확인이 필요한 차이”로 표시하며, 어느 자료가 맞는지·책임이 누구에게 있는지·법률 결론인지는 판단하지 않는다.

완료 기준:

- 분석 응답에 충돌 후보가 포함된다.
- 단일 자료 분석 결과와 기존 저장 분석의 호환성이 유지된다.
- 다중 자료의 서로 다른 날짜·금액과 동일 값 중복을 테스트한다.
- 프론트에 검토 안내로 표시한다.

구현: 날짜(`YYYY-MM-DD`, `YYYY.MM.DD`, `YYYY/MM/DD`)와 금액(쉼표 또는 원 표기)을 자료별로 비교한다. 서로 다른 값이 발견되면 분석 결과의 `conflicts`에 자료 번호와 값을 표시한다. 단일 자료에서는 기존 응답을 그대로 유지하고, 동일 값만 있는 다중 자료는 충돌로 표시하지 않는다.

검증: `LegalDraftServiceTest`의 다중 자료 결합·날짜/금액 차이·기존 단일 자료 회귀, Java 전체 테스트, UI 테스트, OpenAPI YAML 파싱, `git diff --check`.

다음 단계: 사건 도메인 분리.

## 2. 사건 도메인 기반 — 완료

기존 `casework.cases.dispute_domain` 컬럼을 API·조회 모델·프론트에 연결했다. 기존 사건의 null 값은 `housing_lease`로 보정하고, 생성 요청은 `housing_lease`, `vehicle_accident`, `assault`만 허용한다. 차량 사고와 폭행 선택지는 데이터·검색·프롬프트가 준비되기 전까지 화면에서 비활성화한다. 따라서 이번 단계는 분류 저장 기반만 만들었으며, 비주택 법률 답변을 지원한다고 표시하지 않는다.

검증: 사건 통합 테스트, Java 전체 테스트, UI 테스트, OpenAPI YAML 파싱, `git diff --check`.

다음 단계: 차량 사고 법률 데이터·검색어·프롬프트·평가 추가.

## 3. 사건 도메인과 법률 검색 연결 — 완료

사건 증거 검색이 사건의 `dispute_domain`을 읽고 법률 검색에 전달하도록 연결했다. `housing_lease`는 기존 용어 보완과 태그 검색을 그대로 사용하고, 다른 도메인은 해당 도메인 태그만 검색한다. 아직 차량 사고 법률 문서를 적재하지 않았으므로 차량 사고 결과는 빈 근거로 남으며, 주택 법령이 잘못 섞이지 않는다.

검증: 주택 검색 기존 회귀, 사건 검색 컴파일·통합 테스트, Java 전체 테스트, UI 테스트, OpenAPI YAML 파싱, `git diff --check`.

차량 사고 검색어 보완 규칙도 추가했지만, 법령 데이터가 적재되기 전까지는 검색 결과를 노출하지 않도록 화면 선택을 비활성화한다.

## 4. 차량 사고 법령 적재 경로 — 완료

공식 법령 API에서 도로교통법, 교통사고처리 특례법, 자동차손해배상 보장법과 관련 민법 조문을 `vehicle_accident` 태그로 수집할 수 있도록 `collect-vehicle` 명령과 파서를 추가했다. 기존 `collect`는 주택 임대차 적재만 수행한다. 실제 로컬 DB 수집·임베딩과 차량 검색 확인까지 완료했으며, 아직 판례 데이터는 포함하지 않는다.

검증: 차량 도메인 파서 태그 단위 테스트, Java 전체 테스트, UI 테스트, OpenAPI YAML 파싱, `git diff --check`.

차량 도메인 검색 결과가 실제로 존재할 때는 생성 프롬프트에도 차량 사고 도메인이 전달되도록 연결했다. 데이터가 없는 도메인은 주택 법령을 섞지 않고 빈 근거로 처리한다.

실제 검증에서 도로교통법 197개, 자동차손해배상 보장법 80개, 교통사고처리 특례법 6개 선택 조문을 임베딩했다. 차량 사고 질문으로 상위 8개가 자동차손해배상 보장법 조문으로 반환되는 것을 확인한 뒤 차량 사고 선택을 화면에서 활성화했다.

## 5. 차량 사고 실제 사진 검증 — 완료

사용자가 제공한 `사고테스트이미지.jpg`로 실제 OpenAI OCR·사진 관찰·차량 법률 검색·분석 저장 흐름을 실행했다. OCR은 `[인식 가능한 텍스트 없음]`을 유지했고, 여러 차량의 접촉·전면/측면 파손·도로 파편을 관찰로 반환했다. 사고 원인·시점, 부상, 운전자·소유자, 과실·책임은 미확인으로 유지됐다. 분석은 도로교통법 제54조를 공식 출처와 함께 연결했으며 블랙박스·CCTV·경찰 사고조사 자료를 추가 질문으로 제시했다.

업로드·원본 삭제·분석 저장·멱등 재조회·모바일·다운로드·stale·삭제·로그아웃을 모두 통과했다. 보고서는 `build/live-ui/1789089341068/report.json`에 저장했다.

## 6. 차량 사고 생성 평가 — 완료

차량 손해, 부상 미확인, 사고 후 조치, 프롬프트 삽입이 섞인 4개 질문으로 실제 검색·생성 평가를 실행했다. 네 사례 모두 검색 결과 8개와 구조 검증을 통과했고, 사고 원인·과실 비율·책임·승소율을 확정하지 않았다. 추가 질문은 블랙박스·CCTV·경찰 사고조사 자료·진단서·수리견적서·보험 접수 자료를 중심으로 반환됐다.

보고서: `build/vehicle-draft-evaluation/1789089500866/report.json`.
재실행: `./gradlew.bat importLegalData --args=vehicle-draft-evaluate` (실제 OpenAI 비용 발생).

한계: 4개 가상 질문과 현재 법령만 사용했으며, 판례·실제 보험 약관·전문가 검토·반복 안정성은 확인하지 않았다.

## 7. 폭행 법령 적재·검색 — 완료

형법과 폭행 관련 민법 조문을 `assault` 태그로 수집·임베딩하는 `collect-assault` 경로를 추가했다. 실제 로컬 수집에서 형법 394개, 관련 민법 44개 조문을 선택했고 임베딩을 완료했다. 폭행 질문의 검색 결과는 형법 조문만 반환하며 차량·주택 법령이 섞이지 않는다. 기준 법령은 국가법령정보센터의 [형법](https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=284025) 원문을 사용한다.

검증: `search-assault-check` 실제 실행, Java 전체 테스트, UI 테스트, OpenAPI YAML 파싱, `git diff --check`.

## 8. 폭행 생성 평가 — 완료

상해를 동반한 폭행, 고소 전 자료 준비, 프롬프트 삽입이 섞인 3개 질문으로 실제 폭행 코퍼스 검색·OpenAI 생성을 실행한다. 생성 프롬프트는 폭행 분야로 전달하고, 책임·유죄·승소를 단정하지 않으며 진단서·사진·영상·목격자 등 확인 자료를 질문하도록 검증한다.

보고서: `build/assault-draft-evaluation/<timestamp>/report.json`.
재실행: `./gradlew.bat importLegalData --args=assault-draft-evaluate` (실제 OpenAI 비용 발생).

한계: 현재는 형법·민법 조문 중심이며 판례, 수사기관 절차의 최신 안내, 전문가 검토, 반복 안정성은 후속 범위다.

## MVP 완료 판정

문서에 정의한 개인 사용자용 해커톤 MVP의 핵심 흐름은 완료했다. 인증·인가, 자기 사건 CRUD, 임시 원본 수명 관리, OCR 사용자 확정, 사진 관찰, 다중 증거 충돌 표시, 주택 임대차·차량 사고·폭행 도메인 검색, 공식 출처 표시, 분석·대응 메시지와 프론트 화면을 Java·Node·Chromium·실제 OpenAI 평가로 검증했다.

완료 커밋은 원격에 push하지 않고 `sibaek` 브랜치에만 남겼다. 판례 확대, 법률 전문가 검토, Redis·GraphRAG·파인튜닝, 결제·조직 기능은 MVP 이후 별도 승인 범위다.
- Java·Node·UI·OpenAPI·diff 검증 후 로컬 커밋한다.

## 9. 노동·임금 사건 분야 — 구현 완료

사건 생성·역할 선택·법률 검색어·분석 프롬프트에 `labor` 분야를 추가했다. 근로자·사용자·대리인 역할과 근로계약·임금·퇴직금·해고·근로시간 중심 입력 예시를 제공한다. 공식 국가법령정보센터에서 근로기준법(법령 ID 001872) 및 시행령·시행규칙을 `collect-labor`로 적재할 수 있으며, 데이터가 없는 경우 다른 분야 법령을 섞지 않는다. 법률 답변은 사실관계와 자료 준비 중심으로 유지하며 해고 적법성·체불 확정·청구 가능성을 단정하지 않는다.

검증: `./gradlew.bat test --no-daemon` 통과, OpenAPI YAML 파싱, `git diff --check`. 실제 법령 API 적재·임베딩 및 생성 품질 평가는 다음 데이터 수집 단계에서 실행한다.

## 10. 추가 분쟁 분야 입력 범위 — 완료

소비자 분쟁, 상거래, 가사, 상속, 명예훼손, 개인 상해를 사건 유형과 프론트 선택지에 추가했다. 역할 조합은 서버에서도 검증한다. 전용 법률 데이터가 준비되기 전까지 해당 분야는 사실·증거 정리 중심이며 다른 분야 법령을 검색 결과에 섞지 않는다. 분야별 공식 법령 수집·전문가 검토는 후속 단계다.

## 11. 노동·임금 법령 실제 코퍼스 — 완료

`collect-labor`와 `embed`를 실행해 근로기준법 131개, 시행령 75개 선별 조문(총 206개)을 임베딩했다. `search-labor-check`에서 노동 태그 결과만 반환되는 것을 확인했다. 시행규칙은 공개 API 구조 검증 실패로 자동 적재하지 않았으며, 원문 형식 보정 후 별도 추가한다.
