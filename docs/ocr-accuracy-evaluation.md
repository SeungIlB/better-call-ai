# OCR 정확도 평가 — 2026-09-10

현재 서비스와 같은 `OpenAiOcrRepository`를 직접 호출했다. 실제 OpenAI Responses API에 파일을 전송했으며, 고정 응답 단위 테스트 결과를 인식 정확도로 계산하지 않았다. DB와 사용자 사건은 사용하지 않았다.

## 기준과 결과

가상 문서의 기준은 **문서별 문자 오류율(CER) 1% 이하와 핵심 항목 100% 일치**를 동시에 만족하는 것이다. 금액·날짜·이름·부정 표현·특약 문장에 오류가 하나라도 있으면 평균 CER가 낮아도 실패다. 이 기준은 이번 개발 단계의 평가 기준이며 통계적 품질 보증이 아니다.

CER는 정답 대비 Levenshtein 편집 거리다. Unicode NFC 정규화 후 공백과 `[페이지 N]` 표지만 제외한다. 숫자, 쉼표, 마침표, 부정 표현은 보존한다. 핵심 항목은 값만 찾지 않고 `임차인: 이름`처럼 라벨과 값 또는 전체 문장을 함께 비교한다.

| 실행 | 가상 자료 수 | 문자 오류 / 정답 문자 | CER | 핵심 항목 | 결과 |
| --- | ---: | ---: | ---: | ---: | --- |
| gpt-5.6-terra, 첫 평가 | 7 | 2 / 1,338 | 0.1495% | 60 / 62 | 실패 |
| gpt-5.6-sol, 같은 자료 비교 | 7 | 0 / 1,338 | 0% | 62 / 62 | 통과 |
| gpt-5.6-sol, 별도 문서 추가 재평가 | 8 | 0 / 1,528 | 0% | 69 / 69 | 통과 |
| gpt-5.6-sol, 추론 none·150초 최종 설정 | 8 | 0 / 1,528 | 0% | 69 / 69 | 통과 |

Terra는 선명한 계약서와 4도 기울어진 영수증에서 가상 인물 `윤나래`를 `윤나라`로 읽었다. 작은 글씨 자료에서는 같은 이름을 맞혔다. 따라서 이 결과만으로 해상도 때문이라고 단정하지 않았다. 모델 비교에서는 프롬프트·`detail:high`·입력 이미지·출력 한도를 유지했다. Sol은 동일 자료 비교와 재평가에서 해당 이름을 정확히 읽었다. 정답을 알려주는 프롬프트 추가나 오류 이름에 대한 특수 처리는 하지 않았다.

8건은 선명한 임대차계약서, 작은 글씨 계약서, 표 형태 영수증, 기울어진 JPEG 영수증, 문자 대화 형식 문서, 인쇄된 지시문, 두 페이지 스캔 PDF, 다른 이름·금액의 반환 요청서다. 마지막 요청서는 모델 비교 이후 처음 평가했다. PDF에는 텍스트 레이어 없이 페이지 이미지만 넣었다. 서로 다른 본문은 5종이며 일부 자료는 같은 본문의 변형이다. 69개는 독립적인 사용자 문서 수가 아닌 핵심 항목 출현 횟수다.

재평가 8건은 순차 호출 총 79.62초, 입력 25,629토큰·출력 1,589토큰을 사용했다. 토큰은 API 응답 값이며 청구 금액을 직접 확인한 것은 아니다. 응답 지연과 결과는 실행마다 달라질 수 있다.

최종 설정의 8건 재평가는 총 56.27초, 입력 25,629토큰·출력 1,378토큰이었다. 개발 설정과 `.env.example`에 `OPENAI_OCR_MODEL=gpt-5.6-sol`, `OPENAI_OCR_REASONING_EFFORT=none`, `OPENAI_OCR_TIMEOUT_SECONDS=150`을 반영했다. 추론 설정은 모델별 지원 여부가 다르다. 미설정/빈 값은 API 요청에서 생략한다.

## 재실행

```powershell
# 외부 호출 없이 가상 문서 생성·렌더링
.\gradlew.bat evaluateOcr --args=prepare

# 실제 API 호출: 한 번에 가상 자료 9건. 실행마다 비용 발생.
$env:OPENAI_OCR_REASONING_EFFORT='none'
$env:OPENAI_OCR_TIMEOUT_SECONDS='150'
.\gradlew.bat evaluateOcr --args=gpt-5.6-sol
```

키는 환경 변수 또는 저장소 `.env`의 `OPENAI_API_KEY`를 읽는다. 환경 변수가 우선한다. 키를 명령 인자로 받거나 출력하지 않는다. Windows 기본 한글 폰트는 `C:/Windows/Fonts/malgun.ttf`다. 다른 환경은 한글을 지원하는 TTF 경로를 `OCR_EVAL_FONT`에 지정한다.

결과는 Git에서 제외된 `build/ocr-evaluation/<model>/<timestamp>/`의 `report.json`, `*.expected.txt`, `*.actual.txt`와 원본 이미지/PDF에 저장한다. 보고서는 입력 SHA-256, 모델, 사용량, 소요 시간, 틀린 핵심 항목을 포함한다. 콘솔에는 문서 ID와 점수만 출력한다. 신규 보고서는 실행한 저장소 구현의 SHA-256도 기록한다. 일반 `test`·`check`는 실제 평가 명령을 실행하지 않는다.

실제 호출 실패 시 자동 재호출하지 않고 평가를 중단한다. 품질 기준 미달은 종료 코드 2로 처리하여 Gradle 작업도 실패한다. 일부 자료만 실행된 보고서를 전체 통과로 취급하지 않는다.

## 공개 표준계약서 보조 평가

[법무부 주택임대차표준계약서 PDF(2023-10-06)](https://www.immigration.go.kr/sites/moj/download/20231006_01.pdf)의 첫 두 페이지를 150 DPI PNG로 렌더링해 검사한다. 입력은 빈 공개 양식이며 사용자 개인정보가 없다. PDF 내장 텍스트를 모델에 주지 않는다. 복잡한 표와 여러 단의 읽기 순서는 하나로 정해지지 않으므로 전체 CER 대신 실행 전에 고른 29개 중요 문구를 정확 일치로 확인한다. 원문의 의미를 법률적으로 판단하는 평가가 아니다.

```powershell
New-Item -ItemType Directory -Force build/ocr-evaluation/reference
Invoke-WebRequest 'https://www.immigration.go.kr/sites/moj/download/20231006_01.pdf' -OutFile build/ocr-evaluation/reference/standard-lease.pdf
.\gradlew.bat evaluateOcr --args='prepare public'
.\gradlew.bat evaluateOcr --args='gpt-5.6-sol public'
```

원본 SHA-256은 `9b514b8497bd2cde78969a1111718b1aea2bd9911c49710d7ac676e0683468d5`로 고정한다. 파일 내용이 달라지면 자동 전송하지 않고 중단한다. 보고서는 `public-report.json`에 저장한다. 이 보조 평가의 문구 일치율을 문서 전체 정확도로 표현하지 않는다.

| 모델·설정 | 첫 페이지 | 두 번째 페이지 | 판정 |
| --- | --- | --- | --- |
| Sol, 추론 기본값, 90초 | 14/14, 35.44초 | 응답 완료 실패 | 실패 |
| Sol, 추론 none, 90초 | 14/14, 25.09초 | 응답 완료 실패 | 실패 |
| Sol, 추론 none, 150초 | 14/14, 93.24초 | 15/15, 83.18초 | 29/29 통과 |
| GPT-4.1, 추론 옵션 생략, 90초 | 14/14, 59.79초 | 응답 완료 실패 | 실패 |

실패 실행은 약 90초 대기 제한에서 끝났으나 당시 예외가 공통 오류로 변환되어 공급자 내부 원인까지 확인하지 못했다. 이를 전부 모델 추론 시간 때문이라고 단정하지 않는다. 동일 페이지도 25~93초로 변동했으므로 이번 측정값은 지연 보장이 아니다. 실패 원인 확인을 위해 HTTP 상태와 예외 종류·대기 시간 초과만 기록하도록 보완했다. 문서 본문·키·공급자 오류 본문은 로그에 남기지 않는다.

150초 상한은 3분 실행 예약보다 짧으며, 기한을 넘기거나 미완료된 응답은 여전히 실패로 처리한다. 제한을 없애거나 결과를 임의 절단해 성공 처리하지 않는다. 초기 실패 실행의 보고서는 첫 성공 페이지만 남았으며, 최종 평가 명령은 실패 시도도 기록하고 중단한다.

## 사용자 제공 영수증 검증

사용자가 제공한 실제 전자영수증 캡처 1건(1125×2436 PNG)을 별도로 검사했다. 사용자 이미지·상호·주소·연락처·인식 원문은 저장소에 포함하지 않았으며 로컬 평가 결과만 남겼다. 모델에는 해당 이미지 외 정답을 전달하지 않았다.

확인 항목은 상호, 주문번호의 앞자리 0, 표시 총액, 표 머리글, 메뉴별 이름·단가·수량·금액 4행, 결제금액, 대표자, 사업자번호, 전화번호, 주소, 동·층 표기 총 14개다. 이 수치는 영수증 전체 문자 정확도가 아닌 선정 항목의 일치 여부다.

초기 `detail:high` 실행은 16.74초에 13/14개가 맞았다. 금액은 모두 맞았지만 한자 `生`을 한글로 치환했다. 원본 픽셀을 확대해 정답 문자를 확인했다. `detail:original` 비교도 17.91초에 13/14개였으며 같은 항목에서 다른 한글로 치환했다. 해상도 설정만으로 해결되지 않아 이 설정 변경은 반영하지 않았다.

최종 변경은 전사 지침 한 줄이다. 한자·영문이 섞인 고유명사를 문자 그대로 옮기고 한글 발음이나 익숙한 상품명으로 치환하지 않도록 명시했다. 특정 메뉴명이나 정답 문자는 프롬프트에 추가하지 않았다. 변경 후 첫 실행은 24.57초에 14/14개 일치했다. 자동 치환이나 후처리로 결과를 고치지 않았다.

같은 설정으로 반복한 실행은 54.17초에 13/14개였다. 같은 한자 혼합 항목을 다시 한글로 치환했으므로 **이 지침만으로 오류가 해결됐다고 판정하지 않는다.** 금액·수량·주문번호는 두 실행 모두 일치했다.

추론을 `low`로 바꾼 추가 비교에서도 첫 실행은 14/14개였으나 두 번째 실행은 같은 한자 혼합 항목을 틀려 13/14개였다. 추론 설정 변경으로도 반복 정확도가 확보되지 않았으므로 기본 설정은 `none`으로 유지했다. 이 비교는 동일 영수증 한 장에 한정되며 모델 전체의 정확도나 추론 설정의 일반적인 우열을 나타내지 않는다.

같은 종류의 오류를 다시 확인할 수 있도록 사용자 문서와 별개인 가상 계약 부속표를 평가 자료에 추가했다. `甲`, `乙`, `生`, `現狀`, 영문·숫자 코드의 보존을 확인한다. 평가 명령은 이제 9건을 실행하며, 위 7·8건 결과는 당시 자료 수 기준으로 유지한다.

지침 변경 후 가상 자료 9건은 정답 1,606자에서 편집 오류 0개, 핵심 항목 76/76개 일치였다. 이 결과와 실제 영수증의 반복 오류를 함께 기록한다. 가상 자료 통과가 실제 자료 정확도를 보장하지 않는 사례다.

## 판단과 남은 검증

`gpt-5.6-sol`은 가상 자료 평가를 통과했지만 실제 영수증의 한자 혼합 항목에서 반복 오류가 있어, 사용자 검수 없이 결과를 확정하는 품질 기준은 충족하지 못했다. 이미지/PDF를 지원하는 다른 모델도 API 규격에 맞더라도 같은 정확도를 보장하지 않는다. 모델 교체 시 이 평가를 다시 실행한다.

가상 문서·공개 빈 양식·전자영수증 캡처 한 장으로 실제 촬영물·손글씨·도장 겹침·심한 흐림·잘림·체크박스 선택 상태·30페이지 장문 PDF의 정확도를 입증하지 못한다. 실제 수신 문서의 비식별 표본과 사람이 확인한 정답을 계속 추가해야 한다. 사용자 확정 단계는 계속 필요하며, 다음 검색·분석 기능에는 기계 인식 원문 대신 사용자가 확정한 수정본만 연결한다.

[OpenAI 이미지 입력 문서](https://developers.openai.com/api/docs/guides/images-vision)는 한국어, 작은 글씨, 회전된 이미지의 한계를 안내한다. 이번 결과는 해당 한계가 모든 문서에서 해소됐다는 의미가 아니다. [Sol 모델 문서](https://developers.openai.com/api/docs/models/gpt-5.6-sol)의 규격과 실제 계정 모델 목록을 확인한 뒤 평가했다.
