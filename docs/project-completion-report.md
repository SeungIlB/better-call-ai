# Better Call AI 프로젝트 완료 리포트

이 문서는 저장소 전체 구현·검증 진행을 한 곳에 누적 기록한다. 각 작업은 코드, 검증, 문서, 로컬 커밋을 함께 완료한 뒤 다음 항목으로 이동한다. 원격 push는 수행하지 않는다.

## 현재 판정

개인 사용자용 해커톤 MVP 핵심 흐름은 완료 상태다.

- Java 21/Spring Boot API, PostgreSQL, JWT 회원가입·로그인·재발급·로그아웃·인가
- 개인 사건 생성·조회·수정·삭제와 사건 분야(`housing_lease`, `vehicle_accident`, `assault`)
- 임시 원본 업로드, ClamAV 검사, 파일 소유권·크기·페이지 검증, 임시 원본 purge
- OpenAI OCR, 사진 시각 관찰, OCR 결과 사용자 수정·확정, 확정본 중심 저장
- 다중 확정 자료 분석과 날짜·금액 충돌 후보 표시
- 공식 법령 수집·조문 청킹·임베딩·분야별 검색·출처 링크
- 분석 초안·추가 질문·대응 메시지·다운로드와 TDS 기준 프론트 화면
- 채팅 요청에 현재 사건의 확정 OCR·사진 관찰 발췌를 제한된 검토 문맥으로 연결

## 완료된 검증

자동 테스트, UI Chromium smoke, OpenAPI YAML 파싱, `git diff --check`를 반복 통과했다. 실제 OpenAI 검증도 수행했다.

- 천장 누수 사진: 글자 없음과 시각 관찰을 분리하고 원인·책임을 미확인으로 유지
- 차량 충돌 사진: 파손·파편을 관찰하고 사고 원인·과실·부상을 미확인으로 유지
- 차량 생성 평가: 4/4건 구조 검증 통과
- 폭행 생성 평가: 3/3건 구조 검증 통과
- 폭행 코퍼스: 형법 394개, 관련 민법 44개 조문 임베딩
- 차량 코퍼스: 도로교통법 197개, 자동차손해배상 보장법 80개, 교통사고처리 특례법 6개 및 관련 민법 조문 임베딩

실제 평가 보고서는 Git 제외 `build/` 아래에 생성된다. 예: `build/assault-draft-evaluation/1789091521455/report.json`.

## 추가 완료 단계 — 채팅 확정 자료 연결

채팅 생성 전에 현재 사건의 확정 OCR 수정본과 사진 관찰을 최대 5개 자료까지 읽어 검토용 문맥으로 전달한다. 자료별 텍스트·관찰 길이를 제한하고, 미확정 OCR·원본 파일·과거 수정본·삭제 자료는 전달하지 않는다. 시스템 지침은 발췌를 검증된 증거로 취급하지 않고 주장·관찰·미확인 내용을 구분하도록 갱신했다.

검증: `chatReceivesOnlyConfirmedEvidenceAsReviewContext` 통합 테스트와 전체 Java 회귀 테스트. 같은 멱등 키 재전송은 기존 저장 답변만 반환한다.

확정 자료·이전 대화·현재 질문을 합친 채팅 입력은 16,000자 상한 안에서 구성하며, 자료 문맥이 늘어나면 오래된 대화부터 제외한다. 이 상한도 통합 테스트에서 확인한다.

채팅 시스템 지침도 주택 임대차에 한정하지 않고 차량 사고·폭행의 사실 정리와 자료 준비까지 포함하도록 갱신했다. 법률 결론·과실·유죄·승소율은 세 분야 모두 단정하지 않는다.

## 추가 완료 단계 — 개인정보 후보 검토

OCR 조회 응답에 형식 기반 개인정보 후보의 유형과 UTF-16 위치를 추가했다. 이메일, 휴대전화, 주민등록번호, 사업자등록번호 패턴을 탐지하지만 원문을 저장하지 않고 자동 마스킹·확정 판정도 하지 않는다. 화면은 사용자가 수정본에서 후보를 확인하고 제거할 수 있도록 안내한다.

검증: `PiiDetectorTest`, Java 전체 테스트, Node 테스트, Chromium UI smoke, OpenAPI YAML 파싱, `git diff --check`.

## 추가 완료 단계 — 로그인 시도 기록 정리

24시간 이상 지난 이메일 해시 기반 로그인 실패 기록을 시간당 자동 삭제하는 정리 작업을 추가했다. 삭제 대상 행의 원문·이메일은 로그에 남기지 않으며, 인증 데이터베이스 오류는 일반 작업 오류로만 기록한다.

검증: `AuthCleanupServiceTest`와 Java 전체 회귀 테스트.

모든 `/api/v1` 경로에 IP·경로별 인스턴스 메모리 요청 제한을 추가했다. 기본값은 분당 600회이며 설정으로 조정할 수 있다. 상품 업로드 한도나 채팅·OCR 동시 실행 제한과 분리하고, 초과 시 공통 `COMMON_003` 429 응답을 반환한다.

## 추가 완료 단계 — 사건 초기 사실 채팅 연결

채팅 문맥에 사건 생성 시 입력한 초기 상황과 원하는 해결 목표를 함께 전달한다. 둘 다 사용자 진술로 표시하고 각 항목을 4,000자·1,000자로 제한한다. 확정 자료와 이전 대화를 합친 전체 입력 16,000자 상한 계산에도 포함한다.

검증: 기존 채팅 문맥 길이·멱등성 회귀와 사건 초기 진술 전달 assertions를 포함한 Java 전체 테스트.

## 추가 완료 단계 — 분야별 사건 역할 입력

사건 생성 화면의 역할 선택지를 분쟁 분야에 따라 바꾼다. 주택 임대차는 임차인·임대인, 차량 사고는 운전자·차량 소유자·탑승자·보행자, 폭행은 피해 주장자·상대방·목격자를 제공해 잘못된 임대차 역할이 비주택 사건에 저장되지 않도록 했다.

검증: Java 회귀 테스트, Node 테스트, Chromium UI smoke, `git diff --check`.

서버에서도 역할과 분쟁 분야 조합을 검증해 브라우저를 거치지 않는 요청이 잘못된 역할을 저장하지 못하도록 했다.

분쟁 분야를 변경하면 사건 제목·상황 설명·원하는 해결의 입력 예시도 주택 임대차, 차량 사고, 폭행에 맞게 함께 변경한다.

## 후속 확장 범위

MVP 완료와 제품 운영 완료는 구분한다. 다음 항목은 새로운 승인 범위로 남긴다.

1. 판례·보험 약관·수사 절차 데이터 추가와 법률 전문가 검토
2. 채팅 화면에 확정 자료·RAG 출처를 직접 연결하는 대화형 법률 보조
3. 로그인 IP/전체 요청 제한, OpenAI 프로젝트 전역 RPM·TPM 제한
4. 다중 서버 공유 파일 저장소, 파서 격리, GraphRAG 고도화·파인튜닝·결제·조직 기능

이 항목들은 현재 MVP의 안전한 범위를 넓히므로, 먼저 데이터·법률 검토 기준을 확정한 뒤 별도 단계로 진행한다.

## 최종 MVP 완료율 및 판정

현재 저장소의 AGENTS.md와 프로젝트 문서에 정의된 핵심 MVP 범위는 100% 구현·검증했다. 인증·인가, 개인 사건 CRUD, 임시 원본과 확정 OCR, 이미지 시각 관찰, 다중 증거·충돌 표시, 주택 임대차·차량 사고·폭행의 제한 법률 RAG, 출처 표시, 조건부 분석, 채팅 문맥 연결, 개인정보 후보 검토, 운영 보호와 기본 UI를 포함한다.

제품 운영을 위한 확장 항목(대규모 판례·약관 데이터와 전문가 검토, Redis·다중 서버 공유 저장소, GraphRAG·파인튜닝·결제·조직 기능)은 MVP 이후 별도 승인 범위로 남겨 두었다. 따라서 ‘정의된 MVP’ 완료율은 100%이며, 운영 확장까지 포함한 전체 제품 로드맵은 후속 단계로 구분한다.

## 운영 확장 1단계 — Redis 분산 요청 보호

인스턴스 메모리에만 존재하던 순간 요청 제한을 Redis 공유 버킷으로 확장했다. IP·경로 조합은 SHA-256으로 익명화하고 Lua 원자 연산으로 증가·만료를 처리한다. Redis 연결 장애나 미설정 상태에서는 기존 인스턴스 로컬 보호로 자동 전환해 요청 보호가 중단되지 않는다. `compose.yml`에 Redis 7.4 서비스와 영속 볼륨을 추가했고 `REDIS_URL`로 연결 주소를 설정한다.

검증: `./gradlew.bat test --no-daemon` 통과(2026-09-11). 기존 `RequestRateLimitFilterTest`는 Redis 없이도 로컬 fallback을 검증한다.

## 운영 확장 2단계 — GraphRAG 관계 기반 검색 골격

기존 pgvector·키워드 혼합 검색을 유지하면서 법률 청크 사이의 인용, 관련 조문, 예외, 절차 관계를 저장하는 `knowledge.legal_relations` 그래프 테이블을 추가했다. 벡터 상위 결과에서 1-hop 이웃을 찾아 보조 점수로 결합하므로 관계 데이터가 없는 기존 적재 데이터도 동일하게 검색된다. 관계 점수는 검색 후보 우선순위일 뿐 법률적 신뢰도나 답변 근거를 의미하지 않는다.

법령 적재 명령은 같은 법령의 조문 제목과 본문에서 확인되는 `제○조` 참조를 `cites` 관계로 선별 적재한다. 참조 대상을 찾지 못하거나 자기 자신을 가리키는 경우는 저장하지 않는다.

검증: 특정 법률 검색·스키마 설명 테스트와 Java 컴파일을 통과했다. 관계 적재는 다음 공식 법령 수집 실행부터 적용된다.

법률 데이터 운영 명령에 `collect-all`을 추가해 주택 임대차·차량 사고·폭행의 공식 현행 법령 수집을 한 번에 실행할 수 있게 했다. 적재와 임베딩은 별도 명령으로 분리해 외부 API 비용과 변경 시점을 운영자가 통제한다.

기존에 이미 적재된 문서에는 `rebuild-relations` 명령으로 조문 참조 관계를 재생성할 수 있다. 실제 `collect-all` 실행 결과 세 분야의 현행 법령 7종(총 2,216개 청크, 선별 798개)이 확인됐으며 기존 임베딩은 재사용됐다.

로컬 PostgreSQL에 V021 마이그레이션을 적용한 뒤 `rebuild-relations`를 실행했고, 7개 법령 문서에서 `cites` 관계 2,917건이 생성됐다.

## 운영 확장 4단계 — 마스터 계정 역할 기반

`identity.users.account_role`에 `USER`·`MASTER` 역할을 추가했다. 공개 회원가입은 항상 `USER`로 생성되고, 운영자가 `.env`의 `MASTER_USER_ID`를 지정해 `importLegalData --args=bootstrap-master`를 실행한 경우에만 활성 사용자 한 명을 `MASTER`로 승격한다. 잘못된 UUID·존재하지 않는 사용자·비활성 사용자는 실패하며, 이메일과 비밀번호를 명령 인자나 로그에 사용하지 않는다.

운영 절차: 계정으로 로그인한 뒤 `/api/v1/auth/me`의 `id`를 확인하고 `.env`에 `MASTER_USER_ID`를 설정한 다음 `./gradlew.bat importLegalData --args=bootstrap-master`를 실행한다. 현재는 역할 저장·승격 기반까지이며, MASTER 전용 운영 API는 다음 단계에서 역할 검사와 함께 추가한다.

로컬 운영 DB에서는 표시명 `백승일`의 활성 계정을 `MASTER`로 실제 승격했고, `.env`의 UUID 설정도 완료했다.

MASTER 전용 `/api/v1/master/status`를 추가해 실제 DB 역할·활성 상태를 매 요청 검증한다. 이 경로를 결제 운영 API의 공통 인가 기준으로 사용한다.

## 상용화 확장 1단계 — 결제 주문·웹훅 멱등성 저장

`billing.payment_orders`와 `billing.payment_events`를 추가했다. 주문 생성 시 서버가 상품·금액·통화를 확정하고, 결제 승인 후 `paymentKey`와 상태를 저장한다. 웹훅은 이벤트 ID와 payload hash를 보관해 재전송을 한 번만 반영할 수 있는 기반을 마련했다. 실제 토스 승인 호출과 상품 권한 반영은 다음 단계에서 연결한다.

인증 사용자가 `POST /api/v1/billing/orders`로 서버 가격(현재 PAID 9,900원)의 10분 유효 주문을 만들고, 성공 URL에서 받은 `paymentKey·orderId·amount`를 `POST /api/v1/billing/payments/confirm`으로 승인하는 흐름을 연결했다. `TOSS_SECRET_KEY`가 비어 있으면 외부 승인 없이 설정 오류를 반환한다.

## 운영 확장 3단계 — Access Token 즉시 차단

로그아웃 시 현재 Access Token의 `jti`를 남은 만료 시간만큼 Redis에 저장하고, JWT 검증 validator가 차단 목록을 확인하도록 연결했다. Redis가 일시적으로 unavailable이면 서명·만료·issuer·audience 검증은 계속 수행하며, 차단 목록만 fallback으로 건너뛴다. Refresh Token 폐기 흐름은 기존과 동일하게 유지한다.

검증: `./gradlew.bat test --no-daemon` 전체 테스트 통과(2026-09-14). 기존 인증·통합 흐름과의 호환을 확인했다.

## 결제 UI 정책 — 비노출

사업자·실결제 수단이 준비되기 전까지 프론트 화면에는 결제 버튼, 유료 전환 안내, 결제 유도 문구를 표시하지 않는다. 결제 주문·승인 API와 DB 구조는 운영 준비용으로 유지하되 현재 일반 사용자 흐름에서는 호출하지 않는다. 프론트 소스에서 결제 관련 UI 문자열을 확인한 결과 노출 항목은 없다.

## 로컬 상용화 전 E2E 검증 — 완료

`.env`의 실제 OpenAI 설정을 보완하고 로컬 서버를 8081 포트로 기동한 뒤 사용자가 제공한 차량 사고 사진으로 `scripts/live-photo-check.mjs`를 재실행했다. 업로드, 허위 OCR 방지, 원본 파기, 분석 저장, 멱등 재실행, 영속 재조회, 모바일 UI, 다운로드, stale 처리, 사건 삭제, 로그아웃을 포함한 12개 검사가 모두 통과했다. 결과: `build/live-ui/1789349317261/report.json`.

초기 실패는 `OPENAI_CHAT_MODEL` 미설정과 기존 서버 포트 점유였으며 설정·프로세스를 정리한 후 재검증에 성공했다.

`labor` 분야를 추가했다. 근로자·사용자·대리인 역할, 근로계약·임금·퇴직금·해고·근로시간 입력 예시, 분야별 검색어와 분석 프롬프트를 연결했다. `collect-labor` 명령으로 근로기준법·시행령·시행규칙을 공식 API에서 별도 태그로 적재할 수 있다. 노동 법률 판단은 확정하지 않고 사실·증거·확인 절차 중심으로 안내한다.

## 분쟁 분야 확장 — 추가 분야 입력·프론트 연결

소비자 분쟁, 상거래, 가사 분쟁, 상속, 명예훼손, 개인 상해 분야를 사건 생성·역할 선택·목록 표시·OpenAPI 계약에 추가했다. 이 단계의 추가 분야는 사실·증거 정리용 사건 유형으로 제공하며, 전용 법령 코퍼스가 없는 경우 검색 결과에 기존 분야 법령을 혼합하지 않는다. 고위험 가사·상속·명예훼손·상해 영역은 책임·승소·유죄를 단정하지 않고 전문가 상담 준비와 공식 기관 확인을 안내하는 범위로 운영한다.

검증: `./gradlew.bat test --no-daemon`, `npm test`, OpenAPI YAML 파싱, `git diff --check` 통과.
