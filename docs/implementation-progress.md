# MVP 단계별 구현 기록

2026-09-10 사용자 요청: 매 단계 구현·검증·문서화 후 로컬 커밋. **원격 push 금지.** 별도 “다음” 요청 없이 백엔드 핵심 흐름과 프론트 연결까지 진행한다.

## 실행 순서와 완료 기준

1. 새 질문 평가 → 수정에 쓰지 않은 질문의 검색·생성 결과와 실패를 기록한다.
2. 분석 저장·조회 → 서버가 생성한 검토용 결과만 저장하고 소유권, 중복 실행, 사건/OCR 변경에 따른 무효화를 검증한다.
3. 프론트 연결 → 로그인, 사건 목록·작성, 파일 업로드·OCR 검토, 분석·출처·추가 확인, 대응 메시지 작성·다운로드를 연결한다.
4. 최종 확인 → 브라우저 핵심 흐름·모바일 레이아웃·오류 처리와 실행 가이드를 확인한다.

## 범위와 설계 근거

- 기준: 저장소 AGENTS.md와 최신 사용자 지시. Notion 기능 명세 MVP v0.5, 개발 구현 기준 v1.0, 주제 확장 기획을 확인했다.
- Notion의 더 넓은 미래 범위를 한 번에 구현하지 않는다. 현재 검증된 주택 임대차 근거 기반 안내를 검토용 분석으로 저장하며 승소율·책임 비율·법률 정확도를 보장하지 않는다.
- 화면은 사건 보관함 → 자료 확인 → 근거 기반 검토 → 다음 행동·메시지로 연결한다. 실제 전송·법원 제출·결제·전문가 매칭은 제외한다.
- 사용자가 TSD를 TDS로 정정하고 공식 컴포넌트 안내 URL을 제공했다. TDS의 버튼·배지·목록·탭 구성을 자체 CSS 화면에 반영했다. 상세 기준은 `docs/frontend.md`에 기록했다.
- 단계 완료 시 아래에 변경, 테스트, 남은 한계를 기록한다. Git 이력에서 각 단계의 커밋을 확인할 수 있다.

## 1. 새 질문 평가 — 구현·실제 호출 완료

`importLegalData --args=flow-evaluate-new`를 추가했다. 수정에 사용하지 않은 질문 3개를 호출 전에 고정했고 임베딩·생성을 각 3회 호출했다. 보고서 `1789017172760`: 서버 검증 3/3, 목표 조문 3/4, 평가용 데이터 정리 완료. 난방 긴급 수선·과거 누수 사례는 목표를 찾았지만 전입 이전·보증금 잔액 사례에서 임차권등기 조문을 놓쳤다. 확정일자 자료 확인 근거는 제공했으나 원하는 근거의 완전성을 보장하지 못한다. 현재 법령을 장래 시행으로 표현하거나 반환·전출 안전을 보장한 답변은 관찰되지 않았다. 과거 사건 요약의 법률 설명 혼입은 남아 있다.

새 평가 결과에 맞춰 검색이나 프롬프트를 다시 튜닝하지 않았다. 결과 저장과 UI는 **검토용 안내**로 제공하고 근거가 없으면 정보 부족을 그대로 표시한다. 저장 기능을 법률 정확성 승인으로 취급하지 않는다. HTTP/JWT·실제 OCR 인식·법률 전문가 검토는 이 평가 범위 밖이다.

## 2. 분석 저장·조회 — 설계

- `POST /api/v1/cases/{caseId}/analyses`: 파일 ID·질문·사건 버전·발췌 시작점과 UUID 요청 키. 서버에서 생성한 결과만 저장한다.
- 기존 `aiops.analysis_runs`를 사용한다. 요청 예약은 짧은 트랜잭션, 외부 호출은 트랜잭션 밖, 저장 전 사건 버전·확정 수정본을 다시 검증한다.
- 동일 키·동일 입력은 저장 결과를 재사용하고 입력이 다르면 409. 실행 중 예약은 중복 생성하지 않으며 5분 만료 후 실패로 회수한다.
- 사건 진술/OCR 확정 변경은 기존 stale 처리와 연결한다. 조회 응답에는 stale 여부와 사유를 포함한다.
- 결과는 책임 비율·승소 판단 없는 기존 근거 기반 초안이다. 목록·개별 조회 모두 본인 사건만 허용한다.

1단계 검증: 전체 자동 테스트 151개 통과, git diff --check 통과. 원격 push 없이 로컬 커밋.

2단계 완료: 분석 생성·목록·상세 API와 요청 키 재사용, 실패·만료 기록, 사건/OCR 변경 stale 처리를 구현했다. 핵심 통합 테스트 3개 및 전체 154개 테스트 통과. OpenAPI YAML 파싱·git diff --check 통과. 모델 실행 비용 원장·전체 사건 다문서 분석·법률 의미 검증은 이번 저장 단계에 포함하지 않았다.


## 3. 프론트 연결 — 완료

Spring 정적 웹 화면으로 회원가입·로그인 → 사건 생성 → 파일 업로드 → OpenAI OCR 동의·수정·확정 → 저장 분석·출처 확인 → 대응 메시지 편집·TXT 다운로드를 연결했다. 추가 대화도 기존 사실 정리 API에 연결했다. 파일 목록 API를 추가하고 소유권·잘못된 페이지·제거된 파일 제외를 검증했다.

TDS를 참고한 파란 주요 버튼·중립색·탭·배지와 데스크톱/모바일 화면을 구현했다. 저장하지 않은 OCR 변경의 확정을 차단하고, 다른 곳에서 변경된 사건의 분석도 대응 준비 진입 시 다시 조회한다. 네트워크 불확실 시 분석 요청 키를 재사용한다. 실행 방법과 범위는 `docs/frontend.md`를 따른다.

### 남은 한계와 다음 우선순위

이번 완료 범위는 개인 주택 임대차의 검토용 MVP다. 분석은 확정 자료 한 개의 발췌이며 다문서 종합 분석이나 확정적 법률 판단이 아니다. 새 질문 평가의 목표 조문 누락 및 요약에 법률 설명이 섞이는 문제는 남아 있다. 실제 다양한 문서 OCR 평가와 전문가 검토, 새 질문 기반 검색 평가를 먼저 확대해야 한다. 결제·공식 제출·자동 전송·전문가 연결은 구현하지 않았다.

로컬 화면은 `http://localhost:8080/`에서 확인한다. 서버가 종료되면 `./scripts/run-local.ps1`로 실행한다. 실제 분석·대화는 `.env`의 `OPENAI_CHAT_MODEL` 설정이 필요하다. 현재 환경의 값은 임의로 변경하지 않았다.

## 5. 실제 천장 누수 사진 검증 — 완료

첫 실제 검증의 업로드 503은 OpenAI 오류가 아니었다. `compose.yml`에 ClamAV 서비스가 정의돼 있었지만 컨테이너가 실행되지 않아 `127.0.0.1:3310` 연결이 실패했고, 서버가 `MALWARE_SCAN_UNAVAILABLE (FILE_008)`으로 안전하게 업로드를 거부했다. ClamAV를 실행한 뒤에는 내부 `clamd` 초기화가 끝날 때까지 기다려야 했다. 포트가 열려도 health 상태가 `healthy`가 되기 전에는 같은 503이 재현됐다.

ClamAV healthy 이후 사용자가 제공한 천장 누수 사진으로 실제 로컬 서버·OpenAI 흐름을 재검증했다. 업로드 201, OCR 3.6초, `[인식 가능한 텍스트 없음]` 유지, 원본 확정 후 삭제, 분석 약 8.2초, 분석 저장·재조회·동일 요청 키 재사용, 모바일 가로 넘침·TXT 다운로드·사건 변경 stale 처리가 모두 통과했다. 분석 결과는 사진의 글자 부재와 사용자 진술을 구분하고 원인·책임을 만들지 않아 `INSUFFICIENT_EVIDENCE`와 추가 질문을 반환했다.

재현 스크립트는 `scripts/live-photo-check.mjs`이며 실제 키가 필요한 수동 실행 전용이다. 보고서는 `build/live-ui/1789020091391/report.json`에 저장했다. 이 단계는 현재 OCR만 연결한 검증이다. 사진의 시각적 관찰 문장을 별도 저장해 RAG에 전달하는 기능은 다음 단계로 남아 있다.

## 6. 사진 관찰 결과 연결 — 완료

OCR 응답을 전사 텍스트만 받는 구조에서 `text`, `observations`, `unknowns` JSON 구조로 확장했다. 결과는 기존 `casework.file_extractions.vision_json`에 저장하고 OCR 화면에서 사용자가 확인한다. 확정 자료를 RAG에 전달할 때 관찰 JSON도 함께 전달하며, 시스템 프롬프트는 관찰을 원인·책임으로 바꾸지 않도록 제한한다.

주신 천장 누수 사진으로 실제 OpenAI 연동을 재검증했다. 사진 관찰은 “천장 표면의 긴 얼룩과 일부 돌출·벗겨짐처럼 보이는 부분”으로 반환됐고, 원인·발생 시점·내부 수분·손상 범위·책임 소재는 미확인으로 유지됐다. 분석은 사용자 진술과 사진 관찰을 함께 요약했으며 `INSUFFICIENT_EVIDENCE` 상태를 유지했다. 업로드·OCR·원본 삭제·분석 저장·멱등 재조회·stale·모바일·다운로드까지 통과했다.

전체 JVM 테스트 156개, UI 테스트 3개와 고정 API Chromium 흐름을 통과했다. 실제 보고서는 `build/live-ui/1789021750601/report.json`에 저장했다. 다음 품질 과제는 관찰 결과를 사용자가 직접 수정·확정하는 별도 편집 UI와 관찰 내용에 대한 전용 회귀 평가다.

## 7. 관찰 결과 사용자 확정 — 완료

사진 관찰·미확인 내용에 한 줄 입력 영역을 추가하고, OCR 수정본 확정 요청에 함께 전송해 `vision_json`을 갱신하도록 연결했다. 사용자가 OpenAI의 관찰을 고치거나 제거한 뒤 확정할 수 있으며, 이후 RAG는 확정된 값만 읽는다. 기존 원문과 수정본 이력은 유지한다.

JVM OCR 통합 회귀 테스트, OpenAI 응답 파싱 테스트, UI Chromium 흐름, OpenAPI YAML 파싱과 `git diff --check`를 통과했다. 다음 확장은 확정 자료 여러 개를 선택해 자료 간 날짜·금액·내용 충돌을 보여주는 다중 증거 분석이다.

## 8. 다중 증거 분석 — 완료

분석 화면에서 확정 자료를 최대 5개까지 선택할 수 있게 하고, 선택한 각 자료의 발췌문과 사진 관찰을 `[자료 N]` 단위로 합쳐 동일 질문에 전달한다. 서버는 각 자료의 현재 확정본을 다시 확인하고 분석 입력 이력에도 선택된 자료별 OCR revision을 기록한다. 기존 `fileId` 요청은 그대로 지원하며 `fileIds`를 생략하면 단일 자료 분석으로 처리한다. 자료 간 날짜·금액·내용의 충돌을 별도 분류하거나 책임을 판단하는 기능은 포함하지 않았다.

검증 기준: Java 전체 테스트, UI 유틸리티·Chromium 흐름, OpenAPI YAML 파싱, `git diff --check`. 원격 push 없이 로컬 커밋한다.

## 9. 다중 자료 사실 차이 표시 — 완료

다중 자료 분석 결과에 날짜·금액의 자료별 차이를 `conflicts`로 추가했다. 값이 다를 때만 자료 번호와 발견된 값을 검토 후보로 보여주며, 어느 자료가 맞는지·책임이 누구에게 있는지·법률 결론인지는 판단하지 않는다. 단일 자료 결과와 기존 저장 분석의 호환성을 유지했다. 상세 계획과 단계별 검증은 `docs/gap-remediation-progress.md`에 기록한다.

## 10. 사건 도메인 기반 — 완료

기존 `dispute_domain` 컬럼을 사건 생성·조회·목록·프론트 화면과 연결했다. 기존 null 사건은 마이그레이션에서 `housing_lease`로 보정하고, API는 `housing_lease`, `vehicle_accident`, `assault` 값을 사용한다. 차량 사고·폭행의 법률 데이터와 검색은 아직 연결하지 않았고 화면에서도 준비 중으로 표시한다. 다음 단계에서 차량 사고 데이터셋과 도메인별 검색·프롬프트를 추가한다.

## 11. 사건 도메인과 법률 검색 연결 — 완료

사건 증거 검색이 사건 도메인을 읽어 검색 서비스와 태그 필터에 전달하도록 연결했다. 주택 임대차 경로의 기존 검색어 확장은 유지하고, 아직 데이터가 없는 비주택 도메인은 주택 법령을 반환하지 않는다. 차량 사고 데이터 적재와 도메인별 프롬프트·평가는 다음 단계다.

## 12. 차량 사고 법령 적재 경로 — 완료

도로교통법, 교통사고처리 특례법, 자동차손해배상 보장법과 관련 민법 조문을 `vehicle_accident` 태그로 적재하는 `importLegalData --args=collect-vehicle` 경로를 추가했다. 기존 주택 적재 명령과 분리했으며, 적재 후 기존 `embed` 명령으로 임베딩할 수 있다. 로컬 DB에서 실제 수집·임베딩과 차량 검색 확인까지 완료했다. 공식 판례 수집·차량 사고 생성 평가·전문가 검토는 아직 남아 있다.

차량 도메인 검색 결과가 생성 단계까지 전달되고, 생성 지침의 도메인명도 차량 사고로 바뀌도록 연결했다. 차량 사고 법령 적재·임베딩과 실제 생성 평가는 운영 키가 필요한 별도 검증으로 남아 있다.

차량 사고 사건 생성 선택을 화면에서 활성화했다. 실제 차량 검색 확인 명령은 `importLegalData --args=search-vehicle-check`이며, 상위 8개 결과가 자동차손해배상 보장법 조문으로 반환됐다. 생성 모델의 차량 사례별 품질 평가는 다음 단계다.

## 13. 차량 사고 실제 사진 검증 — 완료

사용자가 제공한 차량 충돌 사진으로 실제 OpenAI OCR·관찰·차량 도메인 검색·분석 저장을 검증했다. 글자가 없는 사진에서 OCR 원문은 `[인식 가능한 텍스트 없음]`으로 유지됐고, 파손·파편은 관찰로, 사고 원인·시점·부상·운전자·과실·책임은 미확인으로 반환됐다. 분석은 도로교통법 제54조를 공식 링크와 함께 연결하고 블랙박스·CCTV·경찰 사고조사 자료를 추가 질문으로 안내했다.

전체 흐름 검증 보고서는 `build/live-ui/1789089341068/report.json`이며 재현 스크립트는 `scripts/live-photo-check.mjs`다. 실제 생성 품질 반복 평가와 판례 연결은 아직 남아 있다.

## 14. 차량 사고 생성 평가 — 완료

차량 손해·부상 미확인·사고 후 조치·프롬프트 삽입 4개 사례로 실제 차량 코퍼스 검색과 OpenAI 생성을 평가했다. 4/4 사례가 서버 구조 검증을 통과했고, 결과는 사고 원인·과실·책임·승소율을 단정하지 않았다. 보고서는 `build/vehicle-draft-evaluation/1789089500866/report.json`이며 명령은 `importLegalData --args=vehicle-draft-evaluate`다. 판례와 실제 보험 약관을 포함한 반복 평가 및 전문가 검토는 남아 있다.

## 15. 폭행 법령 적재·검색 — 완료

형법과 폭행 관련 민법 조문을 `assault` 태그로 수집·임베딩하고, 사건 도메인에 따라 폭행 법령만 검색하도록 연결했다. 실제 로컬 검증에서 형법 394개와 관련 민법 44개 조문을 선택·임베딩했으며 고정 폭행 질문 검색 결과는 형법 조문으로 제한됐다.

## 16. 폭행 생성 평가 — 완료

상해 동반 폭행, 고소 전 증거 준비, 프롬프트 삽입 3개 사례로 실제 검색·OpenAI 생성을 실행하는 `assault-draft-evaluate` 명령을 추가했다. 생성 호출에 폭행 도메인을 전달하고 책임·유죄·승소 단정을 차단하며 추가 자료 질문을 확인한다. 보고서는 `build/assault-draft-evaluation/<timestamp>/report.json`에 저장한다.

## MVP 완료 판정

개인 사용자용 해커톤 MVP의 핵심 사용자 흐름과 현재 지원 도메인(주택 임대차·차량 사고·폭행)을 구현하고 자동·브라우저·실제 API 검증을 완료했다. 후속 확장으로 분류한 판례 확대, 전문가 검토, Redis·GraphRAG·파인튜닝, 결제·조직 기능은 이 완료 판정에 포함하지 않는다.

## 17. 채팅 확정 자료 문맥 — 완료

채팅 요청 전에 현재 사건의 확정 OCR 수정본과 사진 관찰을 최대 5개까지 검토 문맥으로 전달한다. 미확정 원문·과거 revision·삭제 자료는 제외하고, 이전 대화·자료·현재 질문의 합계는 16,000자 상한 안에서 구성한다. 채팅 지침은 주택 임대차뿐 아니라 차량 사고·폭행의 사실 정리와 자료 준비를 지원하며 법률 결론은 단정하지 않는다.
## 자료 삭제와 사건 분야 수정 보완

로컬 재기동 중 Tomcat이 사용자 시스템 임시 폴더의 권한 오류로 종료되던 문제를 확인해 `server.tomcat.basedir`와 JVM 임시 폴더를 프로젝트의 쓰기 가능한 `build` 하위 경로로 고정했다.

자료 목록에 소유자 확인 대화상자를 거치는 `자료 삭제` 버튼을 추가했다. `DELETE /api/v1/cases/{caseId}/files/{fileId}`는 자료를 논리 삭제하고 임시 원본 정리를 즉시 시도하며, 사건 버전을 증가시키고 기존 분석을 최신 아님으로 표시한다. 삭제된 자료는 목록·단건·확정 근거에서 404/제외된다.

사건 수정 요청에 `disputeDomain`을 추가해 생성 후에도 분쟁 분야와 역할을 함께 수정할 수 있게 했다. 기존에는 수정 DTO와 SQL에 분야 필드가 없어 화면에서 선택해도 저장되지 않았다. 소유권·버전 충돌·삭제 자료 조회를 통합 테스트로 검증했다.

검증: `./gradlew.bat compileJava --no-daemon`, 자료 삭제 통합 테스트, 분야 수정 통합 테스트, `npm test`, `git diff --check` 통과. 로컬 서버는 `.env`를 읽는 `scripts/run-local.ps1`로 `http://localhost:8080`에서 기동했고, Flyway·JWT 초기화까지 확인했다.
